# 1. Назначение и статус документа

Цель: выявить технические решения (патенты и заявки), близкие к программному средству «ER Editor» (построение схемы базы данных и ER-диаграмм, определение нормальной формы, поиск зависимостей по данным, защитные триггеры), чтобы (а) обосновать раздел о новизне и отличиях в научной статье, (б) оценить риски пересечения с чужими патентами и (в) выбрать способ охраны.

**Это предварительный поиск, а не официальный патентный отчёт по ГОСТ Р 15.011-96 и не заключение о свободе использования.** Он выполнен по открытым веб-источникам (прежде всего Google Patents через поисковую систему). Базы ФИПС, Espacenet и USPTO напрямую не опрашивались, поиск по классификационным индексам не выполнялся, а формулы изобретений для большинства документов не изучались полностью (в доступных текстах пункты формулы не отображались; выводы сделаны по рефератам и описаниям). Правовой статус взят из Google Patents, который сам называет его предположением, а не юридическим заключением.

# 2. Предмет поиска и существенные признаки

| № | Существенный признак средства |
|---|---|
| П1 | Построение схемы БД и инфологической/даталогической ER-диаграмм по текстовому описанию, SQL или файлу SQLite (детерминированный разбор, без обучаемых моделей) |
| П2 | Проверка 1НФ, 2НФ, 3НФ и НФБК по записанным функциональным зависимостям и признакам по структуре и именам; разграничение нарушений (влияют на вердикт) и подозрений (не влияют) |
| П3 | Вывод необъявленных ключей-кандидатов из зависимостей и объявленных ключей, предупреждение об ключе, который не объявлен как UNIQUE |
| П4 | Достигнутая форма как «наименьший уровень нарушения минус один»; объяснение каждого замечания правилом, столбцами и подсказкой, подсветка на схеме |
| П5 | Поиск кандидатов в зависимости по данным загруженной базы с подтверждением человеком и записью в то же поле зависимостей, по которому проверяются формы |
| П6 | Создание базы SQLite по той же схеме: правила ON DELETE (выбор в интерфейсе), значения DEFAULT, предупреждения о противоречиях |
| П7 | Защитные триггеры BEFORE INSERT / BEFORE UPDATE, отклоняющие значения текстовых столбцов по сочетаниям признаков SQL-инъекции |

# 5. Анализ

**Что уже известно из уровня техники.**

- Идея средства проектирования, которое проверяет модель по правилам нормализации и показывает список нарушений с отметками на объектах, опубликована в заявке IBM US20070168334A1 (2007), в том числе правила 1НФ, 2НФ и 3НФ по зависимостям, заявленным пользователем. Заявка оставлена и патентом не стала, но как опубликованный документ входит в уровень техники.
- Проверка зависимостей по значениям данных для нормализации описана в патенте Toshiba US5481703A (1992), срок действия которого истёк; сама логика функциональных зависимостей, нормальных форм и ключей-кандидатов принадлежит общей теории реляционных баз данных (Кодд и последователи) и не охраняется.
- Подходы к построению схемы по тексту известны (IBM US10268699B2), но на неструктурированный текст и с сопоставлением корпусов.

**Что в найденном не обнаружено (по просмотренным материалам).**

- Совмещение в одном средстве: схема из описания или SQL, ER-диаграммы, проверка форм, поиск зависимостей по данным с подтверждением и создание базы (П1–П6).
- Разграничение достоверных нарушений по записанным зависимостям и подозрений по признакам структуры (П2).
- Вывод необъявленных ключей-кандидатов с предупреждением о необходимости объявить UNIQUE (П3).
- Достигнутая форма как «наименьший уровень нарушения минус один» вместе с объяснением (П4).
- Триггер базы данных, отклоняющий значения столбцов по сочетаниям признаков инъекции (П7).

Из этого **не следует**, что решение новое в юридическом смысле: каждый отдельный элемент по существу известен, а оценка новизны комбинации требует чтения формул и отсутствие найденного нельзя считать доказательством отсутствия.

**Риски использования.** Действующие документы с другим механизмом: US10268699B2 (IBM), US12153560B1 (Tableau), US10169378B2 (Oracle), US12682104B2 (Oracle), US10657280B2 и EP2023569B1 (SAP). По описаниям методы существенно отличаются от реализованных в «ER Editor» (другой вход, другая цель или иной уровень защиты), однако **формулы изобретений не изучались**, поэтому утверждать отсутствие пересечения нельзя. Для учебного и научного использования риск представляется малым; перед коммерциализацией необходим анализ формул патентным поверенным.

**Охрана собственного решения.** Алгоритмы проверки нормальных форм основаны на опубликованной теории, ближайшие аналоги (Toshiba, IBM) опубликованы, а в Российской Федерации программы для ЭВМ и математические методы по пункту 5 статьи 1350 ГК РФ сами по себе не признаются изобретениями. Практичный путь — **государственная регистрация программы для ЭВМ** в Роспатенте (статья 1262 ГК РФ) и публикация описания (например, статьёй), которая фиксирует приоритет. Решение о возможном патентовании «как изобретения» (технический результат, не сводящийся к программе и математическому методу) должен принимать патентный поверенный.

# Приложение В. Оговорки

Статус и сроки действия приведены по Google Patents («допущение, а не юридическое заключение»); при оценке рисков нужно проверять фактическое состояние в национальных реестрах (оплата пошлин, переход прав, ограничения). Все ссылки и номера документов приведены по результатам поиска на указанную дату.
